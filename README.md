# LaunchPad — Self-Service Developer Platform

One form (or one CLI command) generates a real, tested Python FastAPI service with a Dockerfile, Helm chart, CI workflow, Backstage catalog entry, and a GitOps deployment state — then, in local mode, you run it and call its business endpoint.

> Personal project. Local completion is verified in [docs/verification.md](docs/verification.md). Backstage UI, kind/Argo CD and AWS/EKS are **configuration delivered, not executed on this machine** (no Docker/kind here) — that boundary is stated plainly in the verification doc, not hidden.

## Quickstart (local, no GitHub token, no Docker needed)
```bash
bash scripts/bootstrap.sh          # Windows: scripts/bootstrap.ps1
python3 scaffold.py create --name demo-orders-731 \
  --description "Demo orders service generated by LaunchPad" \
  --owner team-a --environment dev \
  --output /tmp/demo-orders-731 --gitops-dir /tmp/gitops
cd /tmp/demo-orders-731
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
pytest -q
uvicorn app.main:app --port 8000
curl http://127.0.0.1:8000/api/info
```

## Three implemented capabilities
1. **Validated scaffolding** — service name/owner/environment/description are validated; path traversal, template injection (`${{ }}`, `..`, shell metacharacters) and bad environments are rejected before any file is written (`launchpad/scaffold.py`, tested).
2. **A real generated service** — FastAPI with `/healthz`, `/readyz`, `/metrics`, `/api/info`, pytest suite, non-root Dockerfile, Helm chart (probes, resource limits, non-root, dedicated service account), its own CI workflow and `catalog-info.yaml`.
3. **GitOps update + rollback that persists in Git** — `update` commits a new image tag to the GitOps folder; `rollback` is a `git revert` commit, so Argo CD reconciles the previous version instead of undoing a manual `kubectl` rollback (see gitops/README.md).

## Architecture
Backstage (template/catalog config in `backstage/`) → scaffolder (CLI in `launchpad/`, template in `templates/service/`) → generated service → image (Dockerfile/GHCR in connected mode) → Helm chart → GitOps folder (`gitops/`, Argo CD `Application` config) → kind/EKS cluster (config only here). Diagram + detail: [docs/architecture.md](docs/architecture.md).

## Layout
`launchpad/` scaffolder · `templates/service/` golden-path template · `backstage/` catalog + Software Template · `gitops/` Argo CD app + rollback model · `terraform/aws-eks/` optional AWS/EKS module · `examples/demo-orders-731/` a real generated service (source only) · `scripts/` bootstrap/smoke/cleanup · `tests/` scaffolder tests · `docs/` architecture, demo, decisions, verification.

## Limitations
No Docker/kind on the build machine, so image builds, kind deployment, Argo CD sync and the full Backstage Yarn app were not executed — their files are validated as far as the available tools allow (Helm lint/template, Terraform fmt/validate when binaries are present; results in docs/verification.md). Connected GitHub/GHCR publishing needs a token the local mode deliberately does not require. Public deployment: pending a named account — no public URL is claimed.

## Resume bullets (personal project, only what was demonstrated)
- Built a self-service scaffolder that generates a tested FastAPI service (health/readiness/metrics/info endpoints, Helm chart, CI, catalog entry) from validated inputs, rejecting path-traversal and template-injection attempts.
- Implemented GitOps version update and rollback as Git commits (revert-based), with a locally verified scaffold → test → run → HTTP endpoint walkthrough and recorded timings in docs/verification.md.
